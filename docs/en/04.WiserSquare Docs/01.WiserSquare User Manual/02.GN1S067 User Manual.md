# WiserSquare-GN1S067 User Manual

GN1S067 is an intelligent LoRaWAN tracker developed by RisingHF for cattle and sheep positioning and data monitoring in livestock farming. It features high positioning accuracy, long communication distance and long battery life.

This manual describes how to use GN1S067 on the WiserSquare demonstration platform. For hardware specifications, LoRaWAN remote configuration, APP operation and installation, see the GN1S067 User Manual. For account login and firmware version management of the platform, see [WiserSquare Platform Manual](./01.WiserSquare%20Platform.md).

The sidebar of the home page contains Device List and Electronic Fence, and the top right corner has buttons for Chinese/English switching and user details.
The home page shows the number of devices under the current user, the number of devices currently in alarm and the list of devices currently in alarm.
Click an entry in the current alarm device list to open the device details and query the alarm history of that device.

## 4 Application Data Push

### 4.1 Overview

After the data reported by the device is parsed and stored by the platform, the platform can push that report in real time by `HTTP POST` to the customer's own application server, for integration with third-party livestock management, map display or other business systems.

::: tip

The "iotsquare - Configure the push address" section (1.2) is about the **platform receiving data**: iotsquare pushes the raw uplink of the device to WiserSquare. This chapter, "Application Data Push", is about the **platform sending data**: WiserSquare pushes the parsed, structured data to the customer's own server. The two directions are opposite and the addresses configured are different.

:::

The push is an **application-level** configuration, not a device-level one: one application has one data push address, and all devices associated with that application share it.

Enabling the push takes two steps. The configuration is done by the RisingHF platform administrator; the user only needs to provide a receiving address:

1. Fill in the "Data Push Address" (Push Address) for the application, for example `https://api.example.com/gn1s067/uplink`;
2. Associate the device with that application, that is, set the application the device belongs to.

No device restart is needed after the configuration: the push starts with the next report that is successfully stored. Only an uplink that meets all the following conditions is pushed, otherwise the platform skips it silently, without any error message:

- The device is associated with an application;
- The data push address of that application is not empty;
- The uplink belongs to one of the data report frames listed in 4.5 and has been successfully written to the database.

### 4.2 Request Format

| Item | Description |
|:---|:---|
| Method | `POST` |
| URL | The "Data Push Address" configured on the application, used **as is**; the platform does not append paths such as `/uplink` or `/status` |
| Header | `Contenttype: application/json; charset=utf-8` |
| Body | A `JSON` object, see 4.4 for the fields |
| Response handling | The platform only reads the HTTP status code and logs it; the response body is not parsed and a non-`2xx` status is not retried |

::: warning

- The header name is `Contenttype` (this is how it has always been implemented), not the standard `Content-Type`. If the receiver validates the header, read it by the name `Contenttype`; otherwise ignore the header and parse the body directly.
- The push is **asynchronous and one-shot**: it is not retried and the order is not guaranteed, and pushes not yet sent when the service restarts are lost. A packet re-sent by the device is pushed again (the platform does not de-duplicate by `timeUtc`), so please de-duplicate and sort by `assetUniqueId` + `timeUtc` in the body.
- The current version sends **no authentication information** (no token header). Use a data push address that is hard to guess, or restrict access by source IP on the receiving side.
- The receiver should respond as soon as possible (within 1 second is recommended). The platform sets no timeout for a single push, so a receiver that never responds keeps the connection occupied.
- Latitude and longitude are `float32`: around 113°E the effective resolution of longitude is about `1e-5` degree (about 1 metre), which is sufficient for livestock positioning but must not be used for high-precision measurement.

:::

### 4.3 Message Examples

**Satellite positioning report (with latitude and longitude):**

```json
{
  "assetName": "aabbccddeeff0011",
  "assetUniqueId": "aabbccddeeff0011",
  "battery": 87,
  "humidity": 56,
  "latitude": 22.771235,
  "longitude": 113.12346,
  "productId": "GN1S067",
  "stepCount": 1234,
  "temperature": 25.6,
  "timeUtc": "2026-10-19T08:30:00Z",
  "voltage": 3.62
}
```

**Heartbeat / Bluetooth report (without latitude and longitude):**

```json
{
  "assetName": "aabbccddeeff0011",
  "assetUniqueId": "aabbccddeeff0011",
  "battery": 87,
  "humidity": 56,
  "productId": "GN1S067",
  "stepCount": 1234,
  "temperature": -3.05,
  "timeUtc": "2026-10-19T08:30:00Z",
  "voltage": 3.62
}
```

### 4.4 Fields

| Field | Type | Description |
|:---|:---|:---|
| `assetUniqueId` | string | Device `devEUI`, a 16-character lowercase hexadecimal string |
| `assetName` | string | Device name; currently always identical to `assetUniqueId` |
| `productId` | string | Product identifier, always `GN1S067` |
| `timeUtc` | string | Data collection time, UTC, format `yyyy-MM-ddTHH:mm:ssZ` (second precision); taken from the time reported by the device, not the time the platform received it |
| `temperature` | number | Temperature in `℃`, up to 2 decimal places, may be negative |
| `humidity` | number | Relative humidity in `%RH`, integer, `0`~`100` |
| `battery` | number | Battery level in percent, integer, `0`~`100` |
| `voltage` | number | Battery voltage in `V`, up to 2 decimal places |
| `stepCount` | number | Steps accumulated during the day |
| `latitude` | number | Latitude in degrees, WGS84; **only carried by the satellite positioning report** - other reports do not contain this field at all (it is not `null`) |
| `longitude` | number | Longitude in degrees, WGS84; **only carried by the satellite positioning report** - other reports do not contain this field at all (it is not `null`) |

::: tip

The pushed message is the parsed result of the same report as shown on the platform pages and returned by the query APIs, but it **does not contain alarm information** (neither alarm bits nor alarm records are included); for alarms, see the "Alarm Status History" in 3.8, or query them through the alarm API.

:::

### 4.5 Uplink Types That Trigger a Push

| Device uplink | Function code (2nd byte of the payload) | Pushed |
|:---|:---|:---|
| Satellite positioning report | `0x01` | Yes, with latitude and longitude |
| Heartbeat report (sent when GPS positioning fails) | `0x03` | Yes, without latitude and longitude |
| Bluetooth iBeacon report | `0x05` | Yes, without latitude and longitude |
| Bluetooth Eddystone report | `0x06` | Yes, without latitude and longitude |
| Alarm report | `0x04` | No |
| Version information report | `0x09` | No |
| Responses to query / configuration commands | `0x00`, `0xB0`, `0xB1`, `0xB2`, `0xC0`~`0xC3`, `0xD0` | No |

Note: `0x02` (Bluetooth positioning status report) is deprecated, but if this frame is received it is still handled as a data report and pushed.

### 4.6 Troubleshooting When No Push Is Received

1. Check that the device is associated with an application and that the data push address of the application is not empty;
2. Check that the data push address is reachable from the platform server (the platform sends the request only once, so any failure in DNS resolution, certificate validation or firewall rules makes it fail);
3. Check whether the uplink belongs to one of the frame types marked "No" in 4.5.

## 6 Electronic Fence

An electronic fence is used to determine whether a bound device (an animal) is still inside a given area. The platform compares the satellite positioning coordinates reported by the device with the fence boundary, and whenever the state changes - entering the fence or leaving the fence - an out-of-fence alert is generated for manual review and handling.

The "Electronic Fence" item in the sidebar has two sub-pages:

| Sub-page | Purpose |
|:---|:---|
| Fence Management | View, create, edit and delete fences, and bind fences to devices |
| Fence Alerts | Query, handle and inspect the alerts raised when devices enter or leave a fence |

::: tip How alerts are generated

- Only coordinates carried by a **satellite positioning report** are evaluated; heartbeats, Bluetooth reports and other reports without latitude and longitude are not.
- An alert is generated only when the **state changes** (inside -> outside, or outside -> inside). While a device stays inside or stays outside, repeated reports do not raise repeated alerts.
- The first report of a device only establishes the initial baseline; **no alert is generated**.
- To avoid false alerts from boundary jitter, a report whose position is **less than 1 metre** from the fence boundary is skipped entirely - it neither raises an alert nor updates the baseline.
- A fence whose status is "Disabled" is not evaluated and raises no new alerts. The device may well have walked out of the area while the fence was disabled, so **the first report after re-enabling is compared with the state from before the fence was disabled**, and may therefore raise an alert immediately. This is expected behaviour; the same applies after unbinding and rebinding a device.
- The alert time is the time the platform received the report; it is not affected by the device clock.
- Positions are evaluated in WGS84. The platform converts coordinates automatically while you draw on the map, so users do not need to care about it.

:::

### 6.1 Fence Management

Path: sidebar "Electronic Fence" -> "Fence Management".

The left side of the page holds the filter area and the fence list; the map on the right echoes the polygon of each fence as it is formed (a green area), so you can confirm that the fence location is correct.

The **map type** at the top left is a group of radio buttons: "AMap (Chinese mainland)" or "Google Maps (elsewhere)". Choose according to the region the devices are in. It only determines the base map and the coordinate system actually used, and is **not a list query condition**: switching it updates the map and the fence overlay immediately, but the list itself is not re-filtered.

Filter conditions:

| Filter | Description |
|:---|:---|
| Fence name | Text box, fuzzy search |
| Fence type | Dropdown; currently only "Normal fence" |
| Fence status | Dropdown: Enabled / Disabled |

Buttons: **Search** queries with the current conditions, **Reset** clears them, **Refresh** reloads the list, and **New Fence** starts the creation flow (see 6.2).

The list shows each fence as a card with its name, type tag, status tag and creation time (the card does not show a cumulative alert count). Three buttons sit below each card:

| Button | Action |
|:---|:---|
| Edit | Modify the basic information, the boundary and the bound devices of the fence; the usage is the same as 6.2. The currently bound devices are pre-filled, and **saving takes the "Associated devices" field in the form as the source of truth** - clearing it unbinds all devices |
| Alerts | Jump to "Fence Alerts" and show only the alerts of this fence |
| Delete | Delete the fence and unbind all devices; alerts already generated are **kept**, and still show the fence name as it was at the time in the alert list and in the alert details |

::: warning

Editing and deleting a fence are **allowed only for the user who created it**. Administrator and FAE (technical support) accounts can see fences created by others in the list, but editing and deleting are rejected. A fence can also only bind devices owned by its creator.

:::

### 6.2 Creating a Fence

Click "New Fence" to open the "Fence Editing" page. The whole process has two steps: fill in the basic information first, then draw the fence boundary on the map.

#### 6.2.1 Basic Information

Form on the left:

| Field | Required | Description |
|:---|:---|:---|
| Fence name | Yes | 1 to 64 characters, used to tell fences apart in the list and in alerts |
| Fence type | Yes | Currently only "Normal fence" |
| Fence status | Yes | "Enabled" takes part in out-of-fence evaluation; "Disabled" keeps the fence but does not evaluate it |
| Fence description | No | 0 to 255 characters, may be left empty |
| Associated devices | No | Multiple selection, limited to devices **you own**. Leaving it empty means the fence is bound to no device, and no alert will be generated |

The top of the page offers **quick positioning**: enter the latitude and the longitude separately (a swap button between them exchanges the two in one click if they are the wrong way round), or paste "latitude,longitude" directly into the box on the right, then click "Locate" and the map jumps to that coordinate. "Current location" centers the map on the current browser location.

#### 6.2.2 Drawing the Boundary on the Map

1. Click "Start drawing" to enter drawing mode ("Start drawing" is then greyed out, while "Finish drawing" and "Clear fence" become clickable);
2. Click on the map to add vertices one by one, **at least 3**, going once around the area clockwise or counter-clockwise;
3. Click "Finish drawing" to **create and save the fence**. The vertices are joined automatically into a closed polygon, so there is no need to click the first point again to close the shape; the page has no separate "Save" button;
4. If you draw it wrong, click "Clear fence" and start over.

Editing an existing fence follows the same flow: the existing boundary is echoed on the map first, and redrawing replaces the whole boundary.

::: tip

- The minimum number of vertices is 3; fewer cannot form a polygon and the fence cannot be created.
- Leave some margin around the fence outline: when a device walks right along the boundary, positioning points within 1 metre are ignored, and jitter can easily produce repeated entries and exits.
- The fence should be neither too large nor too small. If it is too large, a device moving inside it can hardly trigger an alert; if it is too small, false alerts increase noticeably.
- One device may be bound to several fences at the same time; each fence is evaluated independently and raises its own alerts. Unless there is a special need, bind only one fence that matches the grazing range, which makes alerts easier to attribute.

:::

### 6.4 Handling an Alert

Click "Handle" at the end of an alert row, or tick several rows and click "Batch handle", to open the "Handle" dialog:

| Field | Required | Description |
|:---|:---|:---|
| Handling status | Yes | "In progress", "Handled" or "Ignored" can be selected. **The status cannot be set back to "Unhandled"** |
| Handling note | No | 0 to 255 characters; describe the verification result, for example "Called the herder and confirmed the herd was moving to another pasture" |

Click "Confirm" to submit. The platform records the handler and the handling time automatically, so there is no need to fill them in, and both are shown in the alert details.

How the three handling statuses are used:

- **In progress**: the alert has been seen and is being verified; mark it first so that others do not handle it again;
- **Handled**: the alert has been verified and dealt with;
- **Ignored**: a false alert or nothing to do (for example, the fence was drawn slightly off, or the device was temporarily moved out).

An alert that has been submitted can be handled again to change the status (for example, change "Ignored" back to "Handled"), and the handling time and handler are updated to those of the latest operation; but **the status can never go back to "Unhandled"** under any circumstances.

### 6.5 Alert Details

Click "Details" at the end of an alert row to open the "Alert Details" dialog, which shows the complete information of the alert:

| Field | Description |
|:---|:---|
| Alert record ID | Unique identifier of the alert record |
| Device | DevEUI of the device that raised the alert |
| Fence ID | ID of the related fence, which can be matched against the fences in the list of 6.1 |
| Fence name | The fence name at the time the alert occurred |
| Battery level | Battery percentage of the device when the alert occurred. In the current version, leave-fence and enter-fence alerts are generated on the server without collecting the battery level, so this value is always `0%` |
| Alert type | Leave fence / Enter fence |
| Handling status | Unhandled / In progress / Handled / Ignored |
| Handler | The account that handled the alert; shows `-` when unhandled |
| Alert time | When the alert occurred |
| Handling time | When the alert was handled; shows `-` when unhandled |
| Position | The device coordinate when the alert was triggered, in the form `latitude,longitude`; click it to open the map |
| Alert message | The description generated by the platform, for example "Device left fence: Company right side" |
| Handling note | The note entered while handling; shows `-` when empty or unhandled |

"Position" is directly clickable: clicking it immediately opens a map with the position of the device at that moment marked, so you can compare it with the fence boundary to judge whether the device really left the fence or the alert was a false one.

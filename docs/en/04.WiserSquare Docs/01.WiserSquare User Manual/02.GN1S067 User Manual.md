# WiserSquare-GN1S067 User Manual

GN1S067 is an intelligent LoRaWAN tracker developed by RisingHF for cattle and sheep positioning and data monitoring in livestock farming. It features high positioning accuracy, long communication distance and long battery life.

This manual describes how to use GN1S067 on the WiserSquare demonstration platform. For hardware specifications, LoRaWAN remote configuration, APP operation and installation, see the GN1S067 User Manual. For account login and firmware version management of the platform, see [WiserSquare Platform Manual](./01.WiserSquare%20Platform.md).

## 4 Application Data Push

### 4.1 Overview

After the data reported by the device is parsed and stored by the platform, the platform can push that report in real time by `HTTP POST` to the customer's own application server, for integration with third-party livestock management, map display or other business systems.

::: tip

The "iotsquare - Configure the push address" section (1.2) is about the **platform receiving data**: iotsquare pushes the raw uplink of the device to WiserSquare. This chapter, "Application Data Push", is about the **platform sending data**: WiserSquare pushes the parsed, structured data to the customer's own server. The two directions are opposite and the addresses configured are different.

:::

The push is an **application-level** configuration, not a device-level one: one application has one data push address, and all devices associated with that application share it.

Enabling the push takes two steps. The configuration is done by the RisingHF platform administrator; the user only needs to provide a receiving address:

1. Fill in the "Data Push Address" (Push Address) for the application, for example `https://api.example.com/gn1s067/uplink`;
2. Associate the device with that application, that is, set the application the device belongs to.

No device restart is needed after the configuration: the push starts with the next report that is successfully stored. Only an uplink that meets all the following conditions is pushed, otherwise the platform skips it silently, without any error message:

- The device is associated with an application;
- The data push address of that application is not empty;
- The uplink belongs to one of the data report frames listed in 4.5 and has been successfully written to the database.

### 4.2 Request Format

| Item | Description |
|:---|:---|
| Method | `POST` |
| URL | The "Data Push Address" configured on the application, used **as is**; the platform does not append paths such as `/uplink` or `/status` |
| Header | `Contenttype: application/json; charset=utf-8` |
| Body | A `JSON` object, see 4.4 for the fields |
| Response handling | The platform only reads the HTTP status code and logs it; the response body is not parsed and a non-`2xx` status is not retried |

::: warning

- The header name is `Contenttype` (this is how it has always been implemented), not the standard `Content-Type`. If the receiver validates the header, read it by the name `Contenttype`; otherwise ignore the header and parse the body directly.
- The push is **asynchronous and one-shot**: it is not retried and the order is not guaranteed, and pushes not yet sent when the service restarts are lost. A packet re-sent by the device is pushed again (the platform does not de-duplicate by `timeUtc`), so please de-duplicate and sort by `assetUniqueId` + `timeUtc` in the body.
- The current version sends **no authentication information** (no token header). Use a data push address that is hard to guess, or restrict access by source IP on the receiving side.
- The receiver should respond as soon as possible (within 1 second is recommended). The platform sets no timeout for a single push, so a receiver that never responds keeps the connection occupied.
- Latitude and longitude are `float32`: around 113°E the effective resolution of longitude is about `1e-5` degree (about 1 metre), which is sufficient for livestock positioning but must not be used for high-precision measurement.

:::

### 4.3 Message Examples

**Satellite positioning report (with latitude and longitude):**

```json
{
  "assetName": "aabbccddeeff0011",
  "assetUniqueId": "aabbccddeeff0011",
  "battery": 87,
  "humidity": 56,
  "latitude": 22.771235,
  "longitude": 113.12346,
  "productId": "GN1S067",
  "stepCount": 1234,
  "temperature": 25.6,
  "timeUtc": "2026-10-19T08:30:00Z",
  "voltage": 3.62
}
```

**Heartbeat / Bluetooth report (without latitude and longitude):**

```json
{
  "assetName": "aabbccddeeff0011",
  "assetUniqueId": "aabbccddeeff0011",
  "battery": 87,
  "humidity": 56,
  "productId": "GN1S067",
  "stepCount": 1234,
  "temperature": -3.05,
  "timeUtc": "2026-10-19T08:30:00Z",
  "voltage": 3.62
}
```

### 4.4 Fields

| Field | Type | Description |
|:---|:---|:---|
| `assetUniqueId` | string | Device `devEUI`, a 16-character lowercase hexadecimal string |
| `assetName` | string | Device name; currently always identical to `assetUniqueId` |
| `productId` | string | Product identifier, always `GN1S067` |
| `timeUtc` | string | Data collection time, UTC, format `yyyy-MM-ddTHH:mm:ssZ` (second precision); taken from the time reported by the device, not the time the platform received it |
| `temperature` | number | Temperature in `℃`, up to 2 decimal places, may be negative |
| `humidity` | number | Relative humidity in `%RH`, integer, `0`~`100` |
| `battery` | number | Battery level in percent, integer, `0`~`100` |
| `voltage` | number | Battery voltage in `V`, up to 2 decimal places |
| `stepCount` | number | Steps accumulated during the day |
| `latitude` | number | Latitude in degrees, WGS84; **only carried by the satellite positioning report** - other reports do not contain this field at all (it is not `null`) |
| `longitude` | number | Longitude in degrees, WGS84; **only carried by the satellite positioning report** - other reports do not contain this field at all (it is not `null`) |

::: tip

The pushed message is the parsed result of the same report as shown on the platform pages and returned by the query APIs, but it **does not contain alarm information** (neither alarm bits nor alarm records are included); for alarms, see the "Alarm Status History" in 3.8, or query them through the alarm API.

:::

### 4.5 Uplink Types That Trigger a Push

| Device uplink | Function code (2nd byte of the payload) | Pushed |
|:---|:---|:---|
| Satellite positioning report | `0x01` | Yes, with latitude and longitude |
| Heartbeat report (sent when GPS positioning fails) | `0x03` | Yes, without latitude and longitude |
| Bluetooth iBeacon report | `0x05` | Yes, without latitude and longitude |
| Bluetooth Eddystone report | `0x06` | Yes, without latitude and longitude |
| Alarm report | `0x04` | No |
| Version information report | `0x09` | No |
| Responses to query / configuration commands | `0x00`, `0xB0`, `0xB1`, `0xB2`, `0xC0`~`0xC3`, `0xD0` | No |

Note: `0x02` (Bluetooth positioning status report) is deprecated, but if this frame is received it is still handled as a data report and pushed.

### 4.6 Troubleshooting When No Push Is Received

1. Check that the device is associated with an application and that the data push address of the application is not empty;
2. Check that the data push address is reachable from the platform server (the platform sends the request only once, so any failure in DNS resolution, certificate validation or firewall rules makes it fail);
3. Check whether the uplink belongs to one of the frame types marked "No" in 4.5.

# WiserSquare Platform Manual

WiserSquare is an intelligent demonstration platform developed on LoRaWAN technology, designed to provide users with a smarter and more convenient demonstration platform. By adopting LoRaWAN technology, WiserSquare can transmit data more stably, and features low power consumption and strong security. On the WiserSquare platform, users can easily demonstrate the functions and performance of IoT devices, sensors, trackers and other products, and monitor their running status in real time to improve the demonstration effect and user experience. Whether an enterprise is demonstrating production line automation or a technology company is demonstrating smart home products, WiserSquare can provide comprehensive support and assistance.

This manual covers account login, firmware version management, and the HTTP APIs that devices use to send uplinks and pull downlinks on the WiserSquare platform. For GN1S067 devices, see [WiserSquare-GN1S067 User Manual](./02.GN1S067%20User%20Manual.md).

## 3 Device HTTP Protocol Access (Uplink)

Besides MQTT, a device can also access the WiserSquare platform directly over HTTP: the device `POST`s its uplink data, and periodically `GET`s the downlink data issued by the platform. This approach is simple to implement and requires no persistent connection, so it suits low-frequency reporting or resource-constrained devices.

### 3.1 Common Request Headers

Every API request must carry the following HTTP headers:

| Field name     | Type   | Description                                                                                     |
|:---------------|:-------|:------------------------------------------------------------------------------------------------|
| x-access-token | string | Signature generated from x-id / x-version and the pre-shared secret using MD5 and Base64        |
| x-id           | string | Unique device ID                                                                                |
| x-version      | string | Software version number                                                                         |
| x-product      | string | Product model, e.g. `GN1S067`                                                                   |

The signature algorithm is `Base64(MD5("<secret>,<device ID>,<software version>"))`: concatenate the secret, the device ID and the software version with commas, compute the MD5 digest, then Base64-encode the digest bytes.

Sample code in Golang that generates the `x-access-token`:

```go
func generateAccessToken(id string, version string, secret string) string {
    digestStr := fmt.Sprintf("%s,%s,%s", secret, id, version)
    h := md5.New()
    _, _ = io.WriteString(h, digestStr)
    digestByte := h.Sum(nil)
    return base64.StdEncoding.EncodeToString(digestByte)
}
```

Sample code in Python that generates the `x-access-token`:

```python
import hashlib
import base64

secret = 'eNQmGcPsU45MrF1v'


def generateAccessToken(id, version):
    md5_obj = hashlib.md5()
    md5_data = f"{secret},{id},{version}".encode("ASCII")
    md5_obj.update(md5_data)
    return base64.b64encode(md5_obj.digest()).decode('ascii')


if __name__ == "__main__":
    assert "wVg7zStI+yAd9OMz/32wJw==" == generateAccessToken("abcdefg", "1.1")
    assert "HCZOMPgolTRJq6ObsLmOQA==" == generateAccessToken("abcdefg", "1.2")
```

### 3.2 Send an Uplink

`POST /api/uplink/push`

Body format: JSON

Request fields:

| Field name | Type   | Required | Description                                                                                              |
|:-----------|:-------|:---------|:---------------------------------------------------------------------------------------------------------|
| data       | string | Yes      | The binary packet bytes converted with base64, e.g. the bytes `[0x31 0x31 0x31]` become `MTEx` in base64 |

Request example:

```json
{
  "data": "MTEx"
}
```

Response fields:

| Field name | Type | Description                                                                   |
|:-----------|:-----|:------------------------------------------------------------------------------|
| code       | uint | 0 means success; a non-zero value means failure, in which case msg holds the reason |

Response example:

```json
{
  "code": 0,
  "msg": ""
}
```

### 3.3 Pull Pending Downlinks

`GET /api/downlink/pull`

This is the non-real-time usage, intended for low-frequency downlinks that the device pulls periodically.

Response fields:

| Field name  | Type   | Description                                              |
|:------------|:-------|:---------------------------------------------------------|
| msgId       | uint   | Unique downlink ID                                       |
| data        | string | The binary packet bytes converted with base64            |
| morePackets | uint   | Whether more packets remain in the downlink queue        |
| code        | uint   | Error code; 0 means success, non-zero means failure      |

Error codes:

| Code | Description                                                            |
|:-----|:-----------------------------------------------------------------------|
| 0    | Success                                                                |
| 404  | No downlink available; in this case the data structure contains nothing |
| Other | msg carries the error information, which can be printed for diagnosis   |

Response example:

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "data": "MTEx",
    "msgId": 8,
    "morePackets": 0
  }
}
```

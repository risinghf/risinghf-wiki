# WiserSquare-RHF1SFE2 User Manual

RHF1SFE2 is a fire extinguisher monitoring terminal developed by RisingHF. It reports the extinguisher's air pressure, temperature, tilt angle, displacement and battery level over LoRaWAN, and raises an alarm by itself as soon as a locally configured threshold is exceeded. It is intended for remote monitoring of extinguisher presence, pressure leakage and tipping.

This manual describes how to use RHF1SFE2 on the WiserSquare demonstration platform, available at `https://wisersquare.risinghf.com/rhf1sfe2/`. For account login and firmware version management of the platform, see [WiserSquare Platform Manual](./01.WiserSquare%20Platform.md).

The sidebar has only two entries, Home and Device List. Looking up a device, setting its thresholds and everything else happens inside the four tabs of Device Details:

| Page / tab | Purpose |
|:---|:---|
| Home | Total devices, devices currently in alarm, and the full alarm history |
| Device List | Adding, querying, deleting and sleeping devices |
| Details | The device's most recent uplink snapshot and current alarm status |
| Data | Raw and decoded data of uplink / downlink frames |
| Alarm History | Every alarm record of that device, one row each |
| Alarm Thresholds | Viewing and editing the alarm thresholds |

::: tip Who does the judging

The thresholds are stored on the **device**, and the limit check is done by the device as well: every uplink carries an "alarm kind + alarm type", and the platform only receives, records and displays it — it never compares values against thresholds itself. A threshold change made on the platform therefore affects alarms only after the device confirms it (see 3.4).

:::

## 1 Home

The Home page has two statistic cards at the top and the alarm history table below.

| Card / block | Description |
|:---|:---|
| Total Devices | Number of devices owned by the current account |
| Devices in Alarm | Number of devices **still in alarm**, counted once per DevEUI. It is derived from whether the device's latest uplink carries an alarm, and drops by one as soon as an uplink without alarm arrives, so it is a real-time value rather than a running total of alarms |
| Alarm History | The alarm records generated by devices, newest first; the refresh icon at the top right of the card reloads them |

Columns of the alarm history:

| Column | Description |
|:---|:---|
| DevEUI | The device that raised the alarm |
| Alarm Kind | Which measurement triggered it, shown as a tag, e.g. "Battery Alarm" |
| Alarm Type | How the limit was exceeded, e.g. "below the configured lower threshold" |
| Created At | When the platform recorded the alarm |
| Action | "Details" shows the details of that single alarm record |

::: warning

Alarm records are **neither de-duplicated nor suppressed**: as long as an uplink still carries an alarm, a new record is written. An alarm left unattended therefore keeps accumulating at the reporting interval (the battery alarm in the screenshot below is written once an hour).

:::

### 2.1 Adding a Device

Click "Add Device" at the top left to open the registration dialog and fill in the actual parameters of the device. Fields marked with a red asterisk are mandatory.

---

![deviceCreate](https://risinghf-wiki.oss-cn-shenzhen.aliyuncs.com/upload/wisersquare/rhf1sfe2/20261027_RHF1SFE2%E8%AE%BE%E5%A4%87%E6%B3%A8%E5%86%8C.png)

---

| Field | Description |
|:---|:---|
| Device Name | A name of your choice, used to tell devices apart in the device list and in alarm records |
| DevEUI | Globally unique LoRaWAN device identifier |
| AppEUI | Globally unique LoRaWAN application identifier |
| Frequency Region / Subnet Type | Select the frequency region and subnet type of the device; must match the region the device was provisioned for |
| Protocol Version | LoRaWAN protocol version, `1.0.2` by default |
| DevAddr | Device network address; together with NwkSKey it forms the unique network identity |
| AppSKey | v1.0 OTAA application session key, used to encrypt application data |
| NwkSKey | v1.0 network session key, used to authenticate network data |
| Product Type | Currently only "Standard LoRaWAN" |

The DevEUI, AppEUI, DevAddr, AppSKey and NwkSKey inputs have a dice button on the right that fills in a random hexadecimal value. **It is a convenience for debugging only**: when registering a real device, enter the actual values printed on the device or given in its join information, otherwise the data the device reports will not reach the platform.

After submitting, the platform registers the device and initializes its threshold configuration in one go; the device appears in the list only when both steps succeed. A failure halfway leaves no partial device behind — simply submit again. DevEUI is unique on the platform, so registering the same DevEUI twice fails.

::: warning Prerequisite

Before adding a device, **the current account must have its network server (iotsquare) access configured**. Clicking "Add Device" without it returns an error and no device is registered, so check first whether the access information of the current account is in place (see the screenshot below).

:::

The access information of the current account can be viewed read-only on the platform: the window lists the ioTSquare address and the open API Token, each with a "Copy" button at the end of the row, and the eye icon shows or hides the value.

### 2.2 Row Actions

| Button | Effect |
|:---|:---|
| Details | Opens the device details page (see chapter 3) |
| Sleep | Sends a sleep command to the device, which then stops reporting periodically. The platform does not track the sleep state; see the device manual for how to wake it up |
| Delete | Removes the device from the platform |

The scope of a deletion is worth knowing:

- The device record, its threshold configuration and its status record on the platform are all deleted;
- **The historical alarm records and uplink / downlink frames are not deleted themselves**, but with the device row gone those old records no longer appear in the alarm history on the Home page;
- A deleted device cannot be restored; registering it again requires the DevEUI and keys once more.

## 3 Device Details

Click "Details" in the device list to open the device details page. There are four tabs at the top: **Details / Data / Alarm History / Alarm Thresholds**, with "Details" selected by default. The "Details" at the end of a row in the Home alarm list is a different one — it opens that single alarm record.

### 3.1 Details

The "Send Async Query" button at the top left sends one query command to the device, asking it to report temperature, pressure, battery, displacement, tilt angle, versions, reporting interval and the associated command list right away. It is **asynchronous**: the click returns immediately and the data refreshes only when the device's response uplink arrives; with the device offline nothing changes.

"Device Info" on the left is the snapshot of the device's most recent uplink:

| Field | Description |
|:---|:---|
| DevEUI | Unique device identifier; the "Copy" button on the right copies it |
| Software Version | Software version reported by the device, e.g. `1.0.7` |
| Hardware Version | Hardware version reported by the device, e.g. `1.2` |
| Displacement | Distance measured by the laser rangefinder (ToF), in `mm`; used to tell whether the extinguisher has been moved |
| Air Pressure | Extinguisher pressure, in `kPa`; used to detect leakage |
| Temperature | Ambient temperature, in `℃`, with two decimal places |
| Power Supply | One of `Battery`, `Mains` or `Not monitored` |
| Battery Level | Battery percentage; meaningful only when the power supply is `Battery` |
| Tilt Angle | Current tilt of the device, in `°`; exceeding the threshold counts as tipped over |
| Reporting Interval | The reporting interval **currently in effect** on the device, in `s` |
| RSSI | Signal strength of the most recent uplink, in `dBm` |
| SNR | Signal-to-noise ratio of the most recent uplink, in `dB` |

All these values come from the device and are not converted by the platform. A field the device has never reported shows as empty or `0` — do not read that as a fault, click "Send Async Query" first.

"Current Alarm Status" on the right shows whether the device is alarming right now: a green tick with "No Alarm" when normal, or the kind and type of the most recent alarm when alarming. It keeps **only the last** alarm and falls back to "No Alarm" as soon as an uplink without an alarm arrives — that is a different thing from the accumulated records in "Alarm History".

### 3.2 Data

The "Data" tab is the frame log between the device and the platform, both uplinks and downlinks.

| Column | Description |
|:---|:---|
| DevEUI | The device the frame belongs to |
| Data | The raw frame as a hexadecimal string, e.g. `00 EA 08 64 00 33 D0 07 5A` |
| Command | Name of the frame's command, e.g. `CFRM` |
| Direction | Uplink is device → platform, downlink is platform → device |
| Push Time | When iotsquare pushed the uplink to the platform. It is the network server time, **not the device clock**, and not the time the platform stored it either |

Click the expand arrow at the start of a row to see the decoded JSON of the frame; the "Copy" button on the right copies the whole block. Fields missing from the decoded result are `null`, meaning **this uplink did not carry that value**, not that the value is 0 — a `CFRM` frame that only carries temperature and pressure, for instance, has `SoftwareVer` as `null`.

Common commands:

| Command | Meaning |
|:---|:---|
| `CFRM` | Periodic report; a single frame may carry temperature, pressure, battery, displacement, tilt and alarms |
| `ALERT` | A standalone alarm report carrying only the alarm kind and alarm type |
| `QACK` | Response to a query command |
| `VER` | Version report |
| `BAT` | Battery report |
| `DPARAM` | Device parameters (versions, reporting interval, associated command list) |
| `PPAT` | List of commands associated with the periodic report |
| `ACKOK` / `ACKERR` | Confirmation of a downlink command, success or failure |

### 3.3 Alarm History

Every alarm record of the device, newest first.

| Column | Description |
|:---|:---|
| DevEUI | The device that raised the alarm |
| Alarm Kind | Which measurement triggered it (temperature, pressure, tilt, displacement, battery), shown as a coloured tag |
| Alarm Type | How the limit was exceeded, shown as text, e.g. "below the configured lower threshold" or "slowly exceeded the configured threshold" |
| Created At | When the platform recorded the alarm |

Three things to keep in mind:

- A single uplink can carry **several** alarms (overtemperature and low battery at the same time, for example); the platform stores each of them, so multiple rows may share the same timestamp;
- Alarm recovery **does not** delete or flag existing records. It only affects "Devices in Alarm" on the Home page and "Current Alarm Status" in the details; the history stays as an audit trail;
- When investigating, read "Alarm Kind" and "Alarm Type" together: for the same pressure alarm, a type of "below the configured lower threshold" means a real leak, while "slowly exceeded the configured threshold" means the pressure dropped gradually over 24 hours — the two call for different handling.

### 3.4 Alarm Thresholds

The seven thresholds are laid out as cards, and "Edit Thresholds" at the top right opens the editing dialog. The card section is titled "Default Threshold Parameters".

| Threshold | Unit | Meaning |
|:---|:---|:---|
| Minimum Air Pressure | `kPa` | Lower limit of the pressure. The device reports a pressure alarm when the pressure falls below it |
| Pressure Step | `kPa` | The device reports a **slow leak** alarm when the pressure drops by more than this within 24 hours |
| Maximum Temperature | `℃` | Upper temperature limit, at most two decimal places. The device reports a temperature alarm when the temperature rises above it |
| Temperature Step | `℃` | The device reports a **rapid temperature rise** alarm when the temperature rises by more than this within 5 seconds, at most two decimal places |
| Maximum Tilt Angle | `°` | The device reports a tipping alarm when the tilt exceeds this; range `0`~`182` |
| Minimum Distance | `mm` | Lower limit of the displacement (rangefinder); range `0`~`2000` |
| Reporting Interval | `s` | Periodic reporting interval of the device, up to `68475` (about 19 hours) |

In the editing dialog DevEUI is read-only and the other seven items are number inputs with a unit suffix; below "Pressure Step" and "Temperature Step" a line of text restates the rule above. Click "OK" to submit, "Cancel" to discard.

Four behaviours of threshold editing are worth knowing in advance; they all come down to "only the device decides":

1. **Items with a value of 0 are not sent**. On submit the platform checks every item; non-zero values are sent as a command, zero values are skipped — so **entering 0 for an item means "leave this item unchanged"**, and 0 cannot be used to switch an alarm off. The dialog pre-fills the current values, so a normal "OK" re-sends all seven items.
2. **It takes effect asynchronously**. After the command is sent the device has to acknowledge it: only on a successful ACK does the platform move the new value from "pending" into the active configuration; on failure or timeout the value stays pending.
3. **Pending values are shown in orange** on the cards. In the screenshot above "Reporting Interval 600 s" is orange while the others are black, and the device details show the device actually reporting every 181 s — orange means "submitted, not yet confirmed by the device". The colour returns to normal, and the value really takes effect, once the device confirms.
4. **Changing thresholds does not recompute history**. Existing alarm records stay as they are; the change only affects the checks that follow.

::: warning

If a change does not take effect, first make sure the device is online and can receive downlinks (the "Data" tab shows whether the downlink record and a matching `ACKOK` uplink are there), then check whether the device is asleep or unpowered.

:::
